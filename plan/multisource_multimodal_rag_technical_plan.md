# 多来源多模态 RAG 技术方案

## 1. 目标

搭建一套支持多来源、多模态信息召回的 RAG 系统，支持：

- 本地搜索与联网搜索
- 文档、图片、视频三类数据
- 根据用户问题动态选择召回范围
- 多路并行召回
- 结果去重、冲突识别和整理
- 基于证据生成最终回答
- 保留来源信息，支持引用与追踪
- 对召回、证据处理、最终回答进行分阶段效果评估

---

## 2. 整体架构

```text
用户
↓
前端
↓
API 层
↓
问题理解
↓
核心引擎
↓
召回任务调度
↓
多路并行召回
↓
结果整理
↓
冲突处理
↓
上下文构建
↓
LLM
↓
最终回答
```

召回能力按照两个维度组合：

```text
             文档    图片    视频
本地搜索       ✓       ✓       ✓
联网搜索       ✓       ✓       ✓
```

一次请求最多触发 6 路召回，也可以根据问题只执行其中部分任务。

实现上采用双层架构：

```text
React 展示层
↓
Python 业务表层
├── FastAPI / 鉴权 / 会话 / 流式响应
├── Query Planner
├── LLM / Embedding / Vision / ASR 通用接口
├── 联网搜索与网页抽取适配器
└── 评估与离线任务编排
↓ gRPC / Protobuf
C++20 核心引擎
├── 请求生命周期与多路并发调度
├── 本地文档 / 图片 / 视频 Retriever
├── 召回结果归一化、去重与确定性冲突规则
├── 上下文与引用构建
└── 索引切分、指纹计算与批量写入
```

Python 与 C++ 默认以独立进程部署，通过版本化 Protobuf 契约通信。只有无需独立扩缩容、不会阻塞 Python 事件循环的纯本地算法，才考虑使用 `pybind11` 作为可选优化。

## 3. 在线流程

### 3.1 API 层

API 层负责：

- 接收用户问题
- 用户身份和权限校验
- 创建请求 ID
- 流式返回回答
- 记录请求日志

建议请求格式：

```json
{
  "query": "介绍 RTX 5090，并找一些图片和评测视频",
  "conversation_id": "xxx",
  "user_id": "xxx"
}
```

内部为每次请求生成 `request_id`，后续所有召回、模型调用和日志都携带该 ID。

### 3.2 问题理解与召回规划

使用一个较小的 LLM 完成：

- 意图识别
- 问题改写
- 子问题拆分
- 判断是否需要本地 / 联网
- 判断需要文档 / 图片 / 视频

要求模型输出固定 JSON，而不是自然语言。

```json
{
  "queries": [
    {
      "query": "RTX 5090 参数和性能",
      "local": false,
      "web": true,
      "document": true,
      "image": false,
      "video": false
    },
    {
      "query": "RTX 5090 产品图片",
      "local": false,
      "web": true,
      "document": false,
      "image": true,
      "video": false
    },
    {
      "query": "RTX 5090 评测视频",
      "local": false,
      "web": true,
      "document": false,
      "image": false,
      "video": true
    }
  ]
}
```

核心引擎只负责执行召回计划，不再自行理解自然语言。

## 4. 核心引擎

核心引擎使用 C++20 实现为独立服务，负责整个请求生命周期。Python API 根据召回计划通过 gRPC 调用核心引擎：

```text
收到召回计划
↓
生成召回任务
↓
并行执行
↓
等待结果
↓
结果统一格式化
↓
结果整理
↓
冲突处理
↓
上下文构建
↓
调用 LLM
```

建议每种召回能力在 C++ 核心中实现统一接口：

```cpp
class Retriever {
 public:
  virtual ~Retriever() = default;
  virtual RetrievalTask Retrieve(
      const Query& query,
      const RetrieveOptions& options) = 0;
};
```

例如：

```text
LocalDocumentRetriever
LocalImageRetriever
LocalVideoRetriever

WebDocumentRetriever
WebImageRetriever
WebVideoRetriever
```

核心引擎只面向统一接口，不关心底层使用的是向量库、搜索引擎还是外部 API。

### 4.1 并行召回

各路召回原则上相互独立，由 C++ 核心使用协程或异步任务并发执行。可采用 C++20 Coroutine + Boost.Asio，并对外暴露 gRPC 异步服务。

```cpp
auto results = co_await WhenAll(
    local_document_retriever.Retrieve(query, options),
    web_document_retriever.Retrieve(query, options),
    web_image_retriever.Retrieve(query, options));
```

每个召回任务设置独立超时，例如：

```text
本地召回：1~2 秒
联网召回：3~5 秒
```

某一路失败时，不影响其他召回结果：

```text
6 路召回
├── 5 路成功
└── 1 路超时

→ 使用成功的 5 路继续回答
```

## 5. 统一召回结果格式

所有召回模块最终转换成统一结构：

```json
{
  "id": "xxx",
  "content": "...",
  "type": "document",
  "source_type": "web",
  "title": "...",
  "source": "...",
  "url": "...",
  "published_at": "...",
  "retrieved_at": "...",
  "score": 0.82,
  "metadata": {}
}
```

其中：

```text
type:
document / image / video

source_type:
local / web
```

`score` 可以保留，但第一版不依赖它进行跨召回模块排序。

## 6. 本地召回

### 6.1 文档

文档先切成多个片段：

```text
Document
├── Chunk 1
├── Chunk 2
├── Chunk 3
└── ...
```

每个片段保存：

```text
chunk_id
document_id
正文
标题
章节
位置
metadata
embedding
```

查询时：

```text
Query
↓
Embedding
↓
向量检索
↓
Top K Chunk
↓
恢复所属文档信息
```

第一版可以采用：

```text
向量检索 + 关键词检索
```

两种方式同时召回，再简单合并去重。

### 6.2 图片

图片入库时提取：

```text
原始图片
↓
图片理解模型
↓
图片描述
↓
图片中文字
↓
图片向量
```

保存：

```text
image_id
image_path
caption
OCR text
embedding
metadata
```

查询时可同时使用：

```text
文本 → 图片语义检索
文本 → OCR 文本检索
```

### 6.3 视频

视频不建议直接以整段视频作为最小召回单位。

离线处理：

```text
视频
├── 字幕 / 语音转文字
├── 场景切分
├── 关键帧
└── 时间戳
```

形成：

```text
video segment
{
  video_id,
  start_time,
  end_time,
  transcript,
  keyframe,
  embedding
}
```

召回时返回具体时间片段，而不是完整视频。

## 7. 联网召回

联网召回与本地召回使用相同接口。

```text
WebDocumentRetriever
↓
搜索引擎 / 搜索 API
↓
网页
↓
正文提取
↓
统一结果格式
```

图片和视频同理。

联网结果必须额外记录：

```text
URL
来源站点
发布时间
抓取时间
```

这些信息后续用于冲突判断。

## 8. 结果去重

多路召回容易出现重复内容，例如：

```text
官方网站
↓
媒体转载
↓
搜索引擎缓存页面
```

第一版可采用三级去重。

### 8.1 URL 去重

完全相同 URL 直接合并。

### 8.2 文本指纹去重

正文归一化后计算 hash，完全相同正文直接合并。

### 8.3 语义去重

对内容向量计算相似度，例如：

```text
similarity > 0.95
```

认为可能高度重复，只保留来源更好的版本。

---

## 9. 冲突处理

不同来源可能对同一问题给出不同甚至相反的结论。

系统需要先判断冲突原因：

- 发布时间不同
- 软件或产品版本不同
- 讨论范围不同
- 实验条件不同
- 统计口径不同
- 来源可信度不同

第一版不需要训练独立模型，可以直接用 LLM 判断。

输入：

```text
用户问题

证据 A
证据 B
证据 C
...
```

输出：

```json
{
  "conflicts": [
    {
      "evidence_ids": ["A", "B"],
      "type": "time_difference",
      "reason": "两份资料发布时间不同"
    }
  ]
}
```

冲突类型可先限制为：

```text
无冲突
时间差异
版本差异
统计口径差异
适用范围不同
真正冲突
无法判断
```

### 9.1 冲突解决原则

优先按确定性规则处理：

```text
时间不同
→ 优先较新信息，同时保留历史信息

版本不同
→ 明确指出对应版本

统计口径不同
→ 分别描述不同口径

范围不同
→ 保留各自适用条件
```

如果仍然无法判断：

```text
不删除任何一方
↓
同时交给最终 LLM
↓
回答中明确说明资料存在分歧
```

不采用简单多数投票。

## 10. 上下文构建

最终不能简单把所有召回结果直接拼接，需要单独的上下文构建模块。

负责：

- 控制总 Token 数
- 去除重复信息
- 保留不同来源
- 保留冲突双方
- 调整内容顺序
- 保存引用编号

例如：

```text
[证据 1]
来源：官方文档
时间：2026
内容：...

[证据 2]
来源：评测网站
时间：2025
内容：...

[证据 3]
来源：视频
时间位置：03:21 - 04:02
内容：...
```

### 10.1 上下文超限

如果召回内容超过上下文长度，第一版使用简单规则：

```text
优先保留：
1. 与问题直接相关的内容
2. 不同来源的信息
3. 冲突信息
4. 官方 / 原始来源

优先删除：
1. 重复内容
2. 高度相似内容
3. 内容过长但信息量低的内容
```

第一阶段不强制引入复杂重排模型。

## 11. 最终生成

LLM 输入：

```text
系统提示词
+
用户问题
+
整理后的证据
```

明确要求：

```text
只能基于提供的证据回答；
如果证据不足，明确说明；
如果证据冲突，指出冲突；
重要事实附带来源编号。
```

最终返回：

```json
{
  "answer": "...",
  "citations": [
    {
      "id": 1,
      "source": "...",
      "url": "..."
    }
  ]
}
```

```text

↓
生成解析任务
↓

↓

↓

```

```text

```


# 16. 效果评估模块

评估模块的目标不是只给最终答案打一个总分，而是回答：

1. 当前版本效果怎么样？
2. 如果回答不好，问题出现在哪个环节？

整体评估链路：

```text
测试问题
↓
召回规划评估
↓
召回效果评估
↓
证据处理评估
↓
冲突处理评估
↓
上下文评估
↓
最终回答评估
↓
性能与成本评估
```

---

## 16.1 测试集

人工构造标准测试问题，每条数据保存：

```json
{
  "question": "RTX 5090 有多少显存？",
  "expected_routes": [
    "web_document"
  ],
  "expected_evidence": [
    "NVIDIA 官方规格页面"
  ],
  "expected_claims": [
    "RTX 5090 配备 32GB 显存"
  ],
  "reference_answer": "...",
  "has_conflict": false
}
```

测试集需要覆盖：

```text
普通事实问题
多来源问题
需要本地资料的问题
需要联网的问题
图片问题
视频问题
需要多路召回的问题
资料版本不同的问题
资料真正冲突的问题
资料不足、应该拒绝下结论的问题
```

需要单独维护一批冲突测试集。

---

## 16.2 召回规划评估

评估问题理解模块有没有调用正确的召回能力。

定义：

```text
必要召回覆盖率
= 正确开启的必要召回 / 应开启的召回

无效召回率
= 不必要的召回 / 实际执行的召回
```

原则：

```text
漏召回
→ 可能导致答案缺失

多召回
→ 通常主要增加延迟和成本
```

第一阶段优先降低漏召回。

---

## 16.3 召回效果评估

当前系统不强调排序，因此核心指标不是“正确文档排第几”，而是：

> 回答问题需要的证据有没有被找到。

定义：

```text
必要证据覆盖率
=
成功召回的必要证据
/
回答问题所需的全部必要证据
```

例如一个问题需要三个事实：

```text
A：发布时间
B：价格
C：显存大小
```

召回覆盖：

```text
A ✓
B ✓
C ×
```

则必要证据覆盖率为：

```text
2 / 3
```

同时按六类召回能力分别统计覆盖率。

---

## 16.4 证据整理评估

重点检查去重和过滤有没有误伤。

主要指标：

```text
重复内容删除率
有效证据误删率
```

其中更重要的是：

```text
有效证据误删率
```

原则：

> 宁愿多保留一点重复信息，也不要错误删除独立证据。

---

## 16.5 冲突处理评估

对于人工标记好的冲突测试数据，评估：

### 冲突发现率

```text
实际存在 100 组冲突
系统发现 91 组

冲突发现率 = 91%
```

### 冲突误报率

没有冲突的资料被错误判断为冲突。

### 冲突原因判断

分别评估：

```text
时间差异
版本差异
统计口径差异
适用范围不同
真正冲突
无法判断
```

例如：

```text
A：2024 年版本支持 32K
B：2026 年版本支持 128K
```

正确结果应是：

```text
版本 / 时间变化
```

而不是：

```text
真正冲突
```

### 无法判断时是否正确保留

对于无法确定谁正确的资料，需要检查系统有没有错误删除其中一方。

---

## 16.6 上下文构建评估

主要记录：

```text
必要证据保留率
重复信息比例
无关信息比例
上下文 Token 数
```

其中：

```text
必要证据保留率
=
进入最终上下文的必要证据
/
已经成功召回的必要证据
```

这样可以区分：

```text
没找到资料
```

和：

```text
找到了资料，但是上下文构建阶段删掉了
```

## 16.7 最终回答评估

主要看四项。

### 1. 正确性

回答中的事实是否正确。

可使用：

```text
人工标准答案
+
LLM 自动评分
```

### 2. 证据忠实度

检查回答里的事实是否真的能从提供的证据推出。

```text
证据忠实度
=
有证据支持的回答事实
/
回答中的全部事实
```

### 3. 完整性

如果标准答案需要：

```text
A
B
C
D
```

模型只回答：

```text
A
B
```

虽然没有错误，但答案不完整。

定义：

```text
答案覆盖的必要信息
/
标准答案的必要信息
```

### 4. 引用正确性

如果回答写：

```text
RTX 5090 拥有 32GB 显存 [1]
```

需要检查：

```text
[1] 是否真的支持这句话
```

而不只是检查 URL 是否存在。

## 16.9 自动评估流程

每次修改核心模块后自动执行完整测试集：

```text
新代码 / 新模型 / 新参数
↓
运行固定测试集
↓
记录完整中间结果
↓
逐层计算指标
↓
与上一版本比较
```

示例：

```text
                 v1       v2

召回规划覆盖率   93%      97%
证据覆盖率       87%      91%
冲突发现率       82%      88%
回答正确率       85%      90%
证据忠实度       94%      93%
P95 延迟          4.1s     5.8s
```

这样能够直接看到效果提升是否伴随明显性能恶化。

## 16.10 线上评估

线上请求随机抽样保存：

```text
用户问题
```

线上重点关注：

```text

事实无证据支持率
用户重新提问率
用户负反馈率

```

## 16.11 第一阶段核心指标

第一版先实现以下 8 个指标：

```text
① 召回规划覆盖率
② 无效召回率
③ 必要证据覆盖率
④ 有效证据误删率
⑤ 冲突发现率
⑥ 最终答案正确率
⑦ 证据忠实度
⑧ P95 延迟 + 单请求成本
```

不建议第一阶段设计统一的“RAG 总分”。

评估模块的首要目标不是排名，而是定位系统瓶颈。

# 17. 第一阶段暂不实现

第一版暂时不引入：

- 复杂重排模型
- 知识图谱
- 独立冲突判断模型
- 复杂多智能体系统
- 学习型召回调度
- 复杂证据评分模型

首先验证核心链路：

```text
问题理解
↓
召回规划
↓
多路召回
↓
证据整理
↓
冲突处理
↓
上下文构建
↓
LLM 回答
↓
分阶段效果评估
```

后续根据实际评测结果，再决定增加哪些模块。
